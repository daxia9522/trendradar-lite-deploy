# Docker 外置运行配置设计与验收边界

## 目标与不变项

- 菜单或宿主机编辑器修改运行配置后，新任务读取新值；不构建镜像、不重新创建常驻容器、不打断已运行任务。
- 配置操作与镜像升级分离，取消配置不得变成构建重试。
- 原生 Linux 的安装脚本、原生菜单默认路径、EnvDocument 默认字面量语义、systemd units/timers、保存事务和任务入口保持兼容。
- `deploy/configure.py` 只增加显式 `--deployment docker --runtime-config` 分支；旧 Docker 顺序向导入口也保留。
- 原生专用文件、`.env.example`、业务 `trendradar/` 与 `weekly_report/` 不为本改造改动。共享解析器不因 Docker 部署目标而改变默认文件格式。

## 配置的边界

| 内容 | 位置 | 生效方式 |
|---|---|---|
| 用户业务配置 | 宿主机 `runtime/env` | 调度轮询/下一任务读取 |
| 镜像、UID/GID、配置页端口等 | 项目根 `.env` / Compose | 明确安装或更新部署 |
| 默认配置模板 | 镜像内 `.env.example`、`config/` | 仅作初始化/缺省值 |
| 运行数据 | `trendradar-output` volume | 与容器生命周期独立 |

常驻容器只读挂载整个 `runtime/` 到 `/app/runtime/`，不挂载单个 env 文件，确保原子替换后下一次 open 看见新 inode。运行文件不放入镜像或 Git；`.dockerignore` 和 `.gitignore` 排除它及备份。

`TRENDRADAR_RUNTIME_ENV` 是新模式的明确边界：存在时必须读取对应文件，不允许缺失/坏配置回退到创建容器时的旧变量；不存在时保留旧的纯环境变量运行模式，便于独立使用旧入口。

新运行文件按字面量解析，不执行 shell、不展开变量。历史 `# TrendRadar env format: docker` 标记保留原 Compose 转义语义。部署模式（Docker）和文件语法（literal / 历史 docker 格式）是不同概念。

## 读取与执行

- 每次从一个安全打开的文件描述符取得完整快照，检查普通文件、路径链接、权限和格式；解析/校验错误只记录固定脱敏信息。
- 运行文件必须为 `0600` 或更严格，目录 `0700`；文件/目录属于常驻非 root 进程对应 UID/GID。
- 新模式仅保留受控的基础进程环境，再叠加最新应用配置；不继承启动时的邮箱、AI、存储、时间参数，避免删除字段后旧值复活。
- 应用变量不能覆盖 PATH/动态链接器等进程执行设置。Docker 身份与本地存储后端锁定。
- `entrypoint.py` 统一处理 scheduler、config-check、doctor、手动日报/强制运行、周报与调度查看。`docker exec` 必须显式调用 `python deploy/docker/entrypoint.py <command>`；直接执行业务模块不会自动经过它。
- 调度器每轮选定已到期业务窗口；每项任务实际派发前重新读取并校验配置，不能沿用前一个长任务启动前的环境。时间签名未变时，已经选定的任务即使因前一个长任务跨分钟而延迟，也携带新环境执行并归属原窗口；不在该轮额外加入后来才到期的任务。时间/时区变化、非法配置或时钟回退则取消剩余待派发任务并重新设定保护窗口。正在执行的子进程保留自己的快照，不因外部保存而改变。
- 初始外置配置、恢复配置或变更时间/时区时跳过当前分钟，避免保存动作立即补跑；后续按正常时间派发。保留窗口重试和部分邮件投递不整批重发规则。
- 无效配置期间不派发新任务，不继续使用旧密钥；恢复后重新建立有效快照。
- 运行文件的大小限制也属于保存契约：超过 1 MiB 的完整文件不能先保存成功、再被任务读取拒绝。
- 完成状态损坏时明确停止派发并要求恢复，不能悄悄清空去重记录继续发信。状态备份/恢复应保留已完成业务窗口；直接删除状态可能导致重复任务。

## 菜单与生命周期

- Docker 分组菜单复用字段定义、单字段输入和脱敏预览；保存由 Docker 适配器完成，不创建 NativeApplication，不调用 systemctl。
- 导入旧配置时，预览的敏感性判定必须覆盖所有允许导入的字段；只有明确登记的普通字段可显示值，未知应用字段保守隐藏。网页纠错期间秘密草稿仅在服务端保存，不能回显到 HTML。
- 默认安装使用兼容的新镜像；源码测试可显式 `--build`。镜像以标签 `org.trendradar.runtime-config=1` 声明支持，旧镜像必须明确拒绝，不把未知参数失败当作取消后自动重建的理由。
- `--configure` / `trendradar-docker` 只使用已在本地的镜像运行临时 setup，保存后退出；不拉取、构建、up 或挂载输出卷。
- `update.sh` 才负责显式镜像升级。已有有效 runtime/env 不覆盖；缺失或需要修正时，安装和升级都进入同一确认菜单。从旧根 `.env` 迁移时保留私有备份，不要求重填已有值，不能静默重解释不支持的插值。升级也安装独立命令入口。
- 安装的路径预检只读；确认保存并校验后才持久化部署身份、安装入口、初始化数据卷并启动。取消不保存 runtime/env、部署身份或迁移备份；不撤销此前明确请求的拉取/构建，也不保证 Docker 自身未创建临时基础设施。
- 非 root 宿主用户与容器使用相同 UID/GID；root 安装使用明确的非 root 身份。输出卷归属初始化仅在明确安装/升级步骤中由独立的 `volume-init` 容器运行；该容器没有网络和项目目录挂载，不能跟随配置保存执行。
- 新运行机制需要一次兼容镜像安装和容器切换；此后业务配置更新不需要再重建容器。

## 验收

1. 原生回归全绿，原生专用文件与基线字节一致；共享默认接口行为不变。
2. Docker 新增、修改、删除配置，特殊字符、旧格式、权限、缺失/非法文件、原子替换均有离线测试。
3. 首次取消、复制模板后的首次安装、重复安装、旧配置确认迁移、升级补齐入口、配置失败不重试构建、陌生命令入口保护、非默认 UID/GID 有模拟测试。
4. 镜像中没有真实配置，常驻服务不再通过 Compose env_file 注入旧业务变量；healthcheck 与人工任务走新入口；镜像带 `org.trendradar.runtime-config=1` 标签，安装器/配置器均校验。
5. JP 只使用独立项目名、测试镜像、临时配置/输出。业务测试禁用真实 AI、发信和远端存储，必要时禁网；验证同一容器 ID 下原子保存后新任务读取新值。
6. 单元测试、打包检查、镜像运行和真实外部服务链路是不同证据层。此任务不验证真实 AI、SMTP 送达或生产迁移。
7. 真机完整链路验收应实际运行安装器、Compose、菜单保存、升级和跨分钟调度，并检查业务输出；不以 `doctor`/`--help` 代替。可使用隔离网络中的协议模拟服务，报告必须明确外部 AI/SMTP 仅被模拟而非已验证真实凭据。

## 同版本镜像重建（维护者）

- 保留既有 Git 标签与版本字段时，可在 `main` 的对应提交 CI 通过后，手动运行 `Release Container Image` 工作流。它从该提交的 `pyproject.toml` 与 `__version__` 校验版本，不接受任意版本或其他分支的手动发布。
- 工作流更新 GHCR 的当前版本标签（如 `v26.9`）与 `latest`，同时发布 `sha-<完整提交 SHA>` 标签；OCI revision 指向本次源码提交。需要固定某一次构建时，使用 SHA 标签或镜像 digest，而不是可更新的版本别名。
- 同版本重建不移动原 Git 标签，也不创建新的 GitHub Release；原标签的源码归档仍是最初发布的源码。发布后分别核对 amd64/arm64 的 revision、version 和 runtime-config 标签。
